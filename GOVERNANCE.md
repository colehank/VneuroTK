# Governance

VneuroTK is a volunteer-maintained open-source project. This document describes how project decisions and maintenance currently work.

## Maintainer

Guohao Zhang (GitHub: [@colehank](https://github.com/colehank)) is the current project lead and maintainer. The maintainer owns releases, repository administration, security coordination, and final decisions about project scope and compatibility.

`CODEOWNERS` requests review; it does not promise a review time or override repository permissions.

## Contributions and decisions

Anyone may propose a change through an issue or pull request. For substantial API, file-format, dependency, or governance changes, open an issue before implementation so the trade-offs can be discussed publicly.

Decisions aim for rough consensus, with particular weight given to reproducibility, maintenance cost, compatibility, data stewardship, and the project's visual-neuroscience scope. When consensus is not reached, the project lead makes the final decision and should record the reasoning in the issue or pull request.

The maintainer may decline work that is out of scope, insufficiently tested, legally unclear, unsafe for research data, or too costly to maintain. Contributors retain copyright in their contributions and submit them under the repository's MIT license.

## Becoming a maintainer

Regular contributors may be invited to maintain the project after demonstrating sustained, constructive contributions, sound technical judgment, and familiarity with the code of conduct and data policy. Maintainer access is granted incrementally and may be removed after prolonged inactivity, at the maintainer's request, or for conduct or security concerns.

If the project lead becomes unavailable, active maintainers should agree publicly on a successor. If no active maintainer remains, the project may be archived rather than presenting unmaintained software as supported.

## Conduct and private matters

Participation is governed by the [Code of Conduct](docs/code_of_conduct.md). Report vulnerabilities through the private channel in the [Security Policy](docs/security.md), not a public issue. Other project questions belong in GitHub issues; see [Support](SUPPORT.md).

This governance model may evolve as the maintainer group grows. Changes to this document are reviewed like other project changes.
